0. 执行摘要

0.1 现状总评（先肯定底座，避免"为改而改"）

v2.1.18 的底座在同类开源项目中属上乘，且比外界对"个人定制分支"的预期扎实得多：

  • 不是空壳原型。仓库自带《v2.1.13-android-crystal-audit》两轮逐链路复核的结论是「其余链路验证为真实管线接线，无假按钮」；functional-modules-audit.md 第十八/二十/二十一轮的机器化矩阵显示：160 条后端命令全部注册且有定义、55 个 emit 事件与 55 个 listen 双向匹配、84 个设置字段 100% 有 Rust 承载、16 个弹窗全部挂载。
  • 非破坏性链路是真的。七大模块的调参最终都落到 adjustments → apply_adjustments → WGSL/CPU 同源管线 → .rrdata sidecar，撤销栈 50 步、AI patch 标记同步、跨图守卫（startPath）、取消语义等工程细节在 v2.1.13 已被集中修过 19 项缺陷。
  • v2.1.18 新增的 AI 调色有真算法。color_transfer.rs（2046 行）实现了 Oklab + MKL 分区协方差传输、3×3 Jacobi 特征分解、bures / robust-bures / mean-cov 三种多样片聚合、黑白参考路由、tone/color 双强度分解；数学层有 114/114 单测覆盖（仓库《language-guided-lut 与透影 Crystal·AI 调色算法深度对比》§六）。
  • 诚实降级是项目既有优点。场景分类 CLIP 未下载时回落像素启发式、LaMa 大面积洞区返回 guidance 而非硬跑、AI 天空模型缺失时走 procedural_sky.rs、未命中风格不猜测。这条纪律应当延续，本方案的所有建议都以「不破坏诚实降级」为前提。

0.2 结论先行：现存问题不在"有没有"，而在四个层次

层次 一句话判断 典型证据
L1 名实不符 部分挂「AI」标签的能力实际是确定性规则/传统重采样，语义理解能力被高估 style_suggest.rs:7-15、platform_features.rs:874-965
L2 端侧可行性落差 若干功能在 Android 真机上不可达、或只在桌面可用、或依赖未验证的云端契约 CrystalAiToolsPanel.tsx:106-108、platform_features.rs:181-201
L3 功能深度不足 原型承诺的子功能被压缩，交互退化为"能点但不够用" crystal.css:127-129、CrystalPreview.tsx:287-289
L4 验证闭环缺失 无真机矩阵、无像素级 golden、无质量回归断言，导致"绿了 CI ≠ 好用" functional-modules-audit.md:535、crystal-boundary-items-implementation-plan.md:165-182

2.1 预设模块（Presets）

2.1.1 已达到的水位（不要重复施工）

usePresetPreviewQueue 缩略图 ≤4 并发 + 代次守卫 + URL 全量 revoke；应用走 applyPresetObject → setAdjustments 进 50 步撤销栈；含 AI 蒙版预设走 ApplyAdjustmentsToPaths + LoadMetadata 重跑蒙版；强度滑杆对蒙版型预设 0% 隐藏、恢复还原；长按卡菜单（450ms）收藏/重命名/删除/覆写/导出；Android content:// 导入导出已在 file_management.rs 修复（functional-modules-audit.md:545-546）；大师 LUT 缺失与 Android APK 资源物化问题已修（:615-655）。

2.1.2 现存缺陷

编号 级别 现象与证据 根因
D-PS-01 P1 AI 推荐卡的场景语义只有 4 类，且置信度门槛是硬编码常数。scene_classify.rs:245 为 SCENE_PROMPTS: [(&str, [&str; 8]); 4]，即风景/人像/夜景/美食；zh-CN.json:463-469 却定义了 5 个场景（多一个「长焦」）；设计目标 W3 原本是 6 类（含街拍/微距，crystal-mobile-improvement-plan.md:294）。DISPLAY_CONFIDENCE_GATE = 0.75（scene_classify.rs:30）为固定值，批内校准只在 CLIP 通道用 24 张窗口 + 中位数兜底（:302-330），启发式通道仍是手工合成分（best_score*…），无概率语义 场景分类以「4 类够用」上线，长焦/街拍/微距未接入；启发式通道与 CLIP 通道置信度语义不统一
D-PS-02 P1 推荐理由与真实依据可能脱节。aiRecommend.sceneBasis「疑似{{scene}} · 依据 {{basis}}」允许 basis = EXIF / 画面分析，而"AI 推荐"标题会让用户以为是视觉识别；仓库《AI功能与其他方面优化改善方案》P0-1 自承启发式对室内人像、暗调美食、夜景人像必然误判，皮肤阈值 R>95 对暗色皮肤系统性偏低 产品文案未区分「EXIF 启发」「像素启发」「CLIP 视觉」三档证据强度
D-PS-03 P2 预设 ↔ 滤镜共用组件实例的状态耦合是"打补丁"式修复。v2.1.13 审计缺陷-预设-1 记录：切分类后 activeId 前缀（preset:/filter:）在另一模式解析不到，状态条/强度/取消入口整体消失而参数仍生效；修复方式是 activeSourceRef 快照回落，而非把两类状态拆成独立实例 组件复用带来的状态域混用，快照回落是兜底不是根治
D-PS-04 P2 配方体系缺数据驱动的校准回路。大师配方 14 条 LUT 为「参考辅助精修 + prior + CanonCGT 伪监督」生成（仓库《language-guided-lut…》§1.1），无样张组学习；同文档 P1-2 提出用 bures 聚合精修大师配方，但 v2.1.18 的 bures 只用于单次追色多样片，未反哺配方资产 配方资产是静态 JSON + 静态 LUT，没有从用户样张回流更新的机制

2.1.3 改善方案

  1. 场景体系扩到 6 类并统一置信度语义（P1）：在 SCENE_PROMPTS 增加街拍/微距两类（每类 8 条中英 prompt ensemble），同步 zh-CN.json 及 15 语言；把启发式通道的 confidence 改造为「与 CLIP 通道同口径的归一化后验」或明确标注 source: heuristic 且不参与 0.75 门槛比较——当前两条通道共用同一门槛但分数不同构，是数值契约错误。保留批内分位数校准，但把窗口参数（SCENE_BATCH_WINDOW=24、FLOOR=0.6、MIN_SAMPLES=8）外提为可配置项并写入诊断报告。
  2. 推荐卡证据分级 UI（P1）：AiRecommendCard 增加三态角标——CLIP 视觉识别 / 画面统计 / EXIF 线索，文案由 basis 精确映射，禁止在低证据档显示"AI 识别"字样；置信度 <0.75 时按既有诚实降级显示"暂无高置信度场景"（zh-CN.json:458 已有文案，直接复用）。
  3. 拆分预设/滤镜状态域（P2）：CrystalPresetsPanel 按 mode 维护两个独立的 activeSource 与 activeId 命名空间（如 useReducer 按 mode 分桶），删除 activeSourceRef 快照回落；补一条回归测试：A 模式应用 → 切 B 模式 → 切回 A，状态条、强度、取消入口三者全部保持可达。
  4. 配方校准回路（P2，观察项）：复用已有 AggregateMode::bures，新增「从 N 张同风格样张生成/精修配方」的离线工具（CLI 即可，不进移动端 UI），输出 .cube + 参数补丁草稿，人工评审后入库。此项依赖真实样张集，不得在无数据时生成配方。

2.1.4 验收

  • 6 类场景 × 每类 20 张离线样张，top-1 准确率与校准前后对比表（真实数据，不填估算值）；
  • 三态角标与 source 字段逐图一致，低证据档不出现「AI 识别」；
  • 预设/滤镜交叉切换 10 轮，无状态丢失；
  • 15 语言 i18n:check 零缺失。

2.2.2 现存缺陷

编号 级别 现象与证据 根因
D-TN-01 P0 二阶传输结果被"反解"成 12+ 个语义滑杆，存在不可逆的信息损失。仓库《language-guided-lut…》§2.1/§2.2 自承：MKL 的 A 矩阵表达"缩放+旋转+平移"（含通道相关性），而本地把任意传输都反解为 colorGrading + curves 控制点，「有信息损失但获得完全可编辑性」；曲线是事后全局单调修正，无法表达色相旋转 非破坏性参数输出与二阶传输精度是内在矛盾，当前只有"反解"一条路径
D-TN-02 P1 多样片聚合的鲁棒性边界未被真实验证。color_transfer.rs 已修两个真 bug（黑白判定 0..255/0..1 域错配、ΔE 下标配对在宽高比不同时越界 panic，见该对比文档 §六），但修复方式是「确定性跨步取模配对」——这解决了崩溃，没有解决统计配对失真：样片与客片尺寸/长宽比不同时，配对像素并非空间对应，ΔE 度量退化为分布采样而非逐像素误差 度量口径为规避 panic 而妥协，缺少「分布级度量」的明确定义
D-TN-03 P1 聚合模式对移动端是"看得见但选不明"。三档 chips（bures / robust-bures / mean-cov，CrystalCategoryPanel.tsx:76-79）无一句适用场景说明；默认 bures，但 robust-bures 的 MAD 软截尾需要 ≥3 张样片才有意义，UI 未做最少样片数提示 高级算法直接暴露给用户，缺适用性引导
D-TN-04 P2 双强度（明暗/色彩）分组是手工枚举。platform_features.rs 的 run_ai_auto_enhance 把 vibrance/saturation/temperature/tint 归色彩组、其余归明暗组（该对比文档 §六），而追色路径的 tone/color 分解作用于 f(x)-x 的 L 轴与 a/b 轴；两条链路的"色彩"语义并不完全对齐，同名滑杆在不同入口效果口径不同 缺少统一的强度语义契约

2.2.3 改善方案

  1. 双载体输出（P0，核心架构改进）：为 compute_color_match 增加 outputMode: "params" | "hybrid"。 - params 保持现状（可编辑、可撤销），但在返回值中明确上报拟合残差（mklInvariantError 已在，color_transfer.rs 已有诊断字段），UI 在残差超阈值时提示"该风格含色相旋转，参数化表达会损失精度，建议改用 LUT 载体"。 - hybrid 新增：把 MKL 仿射传输烘焙成一张 33³ .cube 附属 LUT，写入 adjustments.lutId/lutStrength（复用现有 tetrahedral LUT 链），同时保留参数补丁作为可编辑基底。这样既不破坏非破坏性工作流，又把二阶精度完整保留。前端追色结果卡提供「参数模式 / 高保真 LUT 模式」切换，切换写一次历史。 - 严禁把 LUT 直接覆盖用户已有 lutId；采用 colorMatchLut 独立字段或在 aiPatches 中挂载，避免与特效模块 LUT 冲突。
  2. 度量口径分层（P1）：把 deltaE 明确重命名为 deltaEDistribution（分布级），新增 deltaESpatial（仅在样片与客片同尺寸同取景时计算，否则返回 null 并在 UI 标注"分布度量"）；在返回值补 sampleAspectMismatch、pairedPixels 两个可诊断字段。不再用"取模配对"伪装成逐像素误差。
  3. 聚合模式门禁（P1）：样片数 <3 时禁用 robust-bures chip 并给出本地化说明（新增 1 键 ×15 语言）；bures 默认不变；为每个 chip 加一行副标题说明（"默认/离群样张多时/统计量平均"）。
  4. 统一强度契约（P2）：抽 StrengthDomain 枚举到共享模块，run_ai_auto_enhance 与 compute_color_transfer 共用同一分组定义，并在诊断报告中输出生效的强度系数，保证同名滑杆口径一致。

6.2 AI 推荐卡（证据分级）

  • 卡片三态角标：CLIP 视觉识别（青绿实心点）/ 画面统计（空心点）/ EXIF 线索（灰色虚线点），角标与 scene_classify 返回的 source 字段单一数据源绑定，禁止前端自行推断。
  • 置信度 <0.75 → 卡片降级为「暂无高置信度场景 — 试试 AI 增强」（复用既有 zh-CN 文案），不显示「AI 识别」字样，应用按钮置灰。
  • 切图瞬间：卡片先进入 skeleton（模糊缩略图占位，200ms 淡入），等 selectedImage.isReady（v2.1.13 已修的时序门控）再发起分类；避免旧图场景配方误挂新图。
  • 应用配方：金色胶囊按压态 → pushHistory → 主预览渲染 → toast，全程 不重复弹二次确认（低风险可撤销操作）。

6.3 多样片追色卡片

  • 样片选择区为横向缩略条，每张带「×」移除；数量徽标实时显示 n/5。
  • 聚合模式 chips（bures / robust-bures / mean-cov）：每枚下方 10px 副标题说明适用场景；样片 <3 时 robust-bures 置灰并显示「需 ≥3 张样片」。
  • 「参数模式 / 高保真 LUT 模式」分段控件：切换时结果条同步显示拟合残差 mklInvariantError；高保真模式角标标注「此模式含 LUT 载体」。
  • 追色进行中：进度按 samplePaths 数量分段，取消按钮常驻（复用 CancelAiTask 语义，取消不误报失败）。

6.4 沉浸式裁剪卡片

  • 进入：当前预览区以 transform: scale 平滑放大至全屏（240ms），catnav / bottombar / 二级面板 fade-out 150ms 并 pointer-events: none；.cx-app.is-fullscreen-crop 生效。
  • 内容：三分网格（透明度 0.35，仅手势期间显示，静止 800ms 后淡出至 0.15）、4 角 + 4 边手柄（触控命中 ≥44px，命中时手柄放大 1.15× + 金色描边，120ms）、底部「取消 / 重置 / 确认」三胶囊 + 比例 chips 浮层。
  • 手势：单指拖拽手柄改尺寸（比例锁定）、单指拖框内平移、双指缩放预览、双击 1:1；三态互斥，左上角状态胶囊显示当前模式（见 D-CP-03）。
  • 退出：确认 → 裁剪参数写入并 pushHistory，面板 fade-in 180ms；取消 → 回滚到进入时快照；Android 返回键 = 取消（注册为顶层 exit layer，优先于 confirmModalState 判断，避免 v2.1.3 审计 FD-1 的弹窗冲突回归）。

6.5 AI 能力来源角标与说明条

  • 每格 tile 右上角 6px 圆点：本地模型（青）/ 本地规则（金）/ 云端（紫）；首次点击某类能力时，面板底部滑入一条说明条，150ms fade+slide，说明「是否需要下载模型 / 是否联网 / 是否消耗云端额度」，3 秒后自动收起或用户手动关闭。

8. 结语：与透影 Crystal 品牌调性对齐

这套方案的主线不是"堆功能"，而是把 v2.1.18 已经具备的专业底座，从「能用」推到「名副其实、可验证、端侧可达」：

  1. 诚实是最高优先级的产品资产。项目已经用「未命中不猜测」「模型缺失走程序化天空」「大面积洞区返回 guidance」「不写估算值」建立了很稀缺的信任感。当前最伤这份信任的不是能力弱，而是「一句话调色」被当成语义 AI、「AI 超分」实为 Lanczos、云参考图在 Android 不可达却写在 Release 里。P0 的第一件事就是把名字和能力对齐——这比补十个新功能更能守住品牌。
  2. 非破坏性 + 可编辑性是差异化优势，不该为了精度牺牲。所以 D-TN-01 给的是「双载体」而非「全量烘焙 LUT」：参数模式继续可撤销可微调，高保真模式把二阶传输精度补回来，让用户自己选，而不是替他决定。
  3. 移动端要按移动端做，而不是把桌面同构搬过来。深度图 base64 进 sidecar、Android 恒 CPU、云能力依赖桌面登录态、全屏裁剪 CSS 死代码——这四项的共同根因都是"桌面成立即认为移动端成立"。D-SYS-02 / D-FX-02 / D-CP-01 都指向同一条整改原则。
  4. 没有真机数据就不做静默改动。《AI功能与其他方面优化改善方案》对降噪 tile、XNNPACK、Wi-Fi 开关的处理方式是这份仓库最专业的部分之一；本方案把它写进 §4 并继续保持，所有 _ms / PSNR / Crash-free 数值留待真机采集，不填估算。

按 §5 路线落地 P0 + P1 后，七大模块在「名实相符 / 端侧可达 / 交互深度 / 验证闭环」四个层次上均可对齐 2026 年移动修图主流标杆；而 §4 的"不做清单"能确保团队把资源集中在真正产生用户价值的地方。
