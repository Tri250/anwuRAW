3. 系统架构

PC 浏览器/ Android App→ Nginx 网关→ 应用服务（认证/基础资料/进销存/财务/报表）→ MySQL+ Redis+ 对象存储

应用分层：接口层（Controller）→ 应用服务层（Service，业务规则与事务）→ 领域/数据层（Mapper）。业务规则（FEFO、成本、余额、状态机、权限、审计）集中在 Service 层，两端复用同一套规则，保证 PC/Android 口径一致。

关键边界：

  • 行级数据权限（可访问地点）在数据查询层统一拦截，避免各接口遗漏；
  • 金额统一用整数「分」存储，避免浮点误差；
  • 库存/往来变动一律在事务内完成，配合行锁与流水表保证可追溯。

5. 关键业务算法

5.1 FEFO 批次分配

  1. 锁定目标地点、商品的「在库 / 临期」批次（排除过期、冻结）；
  2. 按 expire_date ASC → inbound_at ASC → batch_no ASC 排序；
  3. 逐批扣减需求数量，直到满足；不足则视为库存不足，事务回滚并提示；
  4. 在单据审核事务内执行扣减并对批次行加行锁（SELECT ... FOR UPDATE），保证并发不超卖。
for batch in available_batches(order.product, order.warehouse):
    take = min(remain, batch.qty)
    batch.qty -= take
    write_ledger(batch, direction=-1, qty=take, biz=order)
    remain -= take
    if remain == 0: break
if remain > 0: raise 库存不足

5.2 批次移动加权平均成本

采购入库时更新批次成本：新成本 = (原库存×原成本 + 入库数量×入库单价) ÷ (原库存 + 入库数量)（结果四舍五入到分）。

销售 / 调拨出库按当前批次 avg_cost 结转成本；毛利 = 售价 − 该批成本。退货回库按原出库成本回补（保证红冲口径一致）。

5.3 应收 / 应付余额

规则：销售审核通过增应收、销售退货审核通过减应收、收款核销减应收（采购方向同理为应付）。

实现：每次变动在事务内同时写 ar_ap_ledger 流水并累加/冲减 customer.balance；查询余额直接读冗余列，对账时以流水重算校验一致。

5.4 红冲与并发控制

  • 红冲：对已审核单据生成一张「反向单据」（数量、金额取负），审核后自动回冲库存与往来；原单标记「已红冲」；不可直接 UPDATE 已审核单据。
  • 并发：扣减走唯一索引 + 行锁；单据号唯一；审核幂等（重复提交不产生双倍库存）。
  • 金额：全程整数「分」，仅在展示层转元。

7. 开发分期

按依赖顺序划分工包，不做时间承诺；每期结束可独立验收、可回归。

阶段交付内容验收要点
S1 框架 + 权限工程骨架、登录认证、角色/账号、地点数据权限、审计日志基座登录、权限隔离、留痕可查
S2 基础资料 + 采购分类/商品/仓库/供应商/客户、采购入库/退货（生成批次与应付）批次入库、应付正确

S4 销售 + 财务销售出库（FEFO）、销售退货、应收应付台账、收款/付款核销、对账单赊销应收、核销、对账平衡
S5 报表 + 移动端核心报表、单据打印、Android 开单/收款/扫码/查库存欠款双端口径一致、现场闭环
